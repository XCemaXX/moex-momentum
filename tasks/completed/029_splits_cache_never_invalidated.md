# `ingest splits` четыре месяца не ходит в сеть

> Создана 2026-09-05 по итогам сквозного ревью репозитория (13 линз, агенты). Срочная, объём S + разбор последствий.

## Проблема

`src/ingest/splits.py:152` кэширует bulk-эндпоинт ISS под фиксированным ключом
`splits/all.json`. У `_read_iss_payload` **нет параметра `force`** (у
`dictionary.py:72` и `dividends/iss.py:68` — есть), а `src/cli/ingest_cmd.py:97-104`
не даёт флага `--force-refresh`.

Замер на диске:

```
.fill_cache/iss/splits/all.json   — 10 мая 2026, 1860 байт, 55 строк
max(tradedate) внутри             — 2026-04-17
```

При этом README и runbook скилла предписывают гонять `momentum ingest splits`
каждый месяц. Майский, июньский, июльский и августовский прогоны были **no-op**:
команда отработала, отчиталась «идемпотентно», прочитала майский файл и не сделала
ни одного запроса.

Пропущенный сплит не даёт ошибку — он даёт неправильное число: едет `close_adj`
(`src/adjustments/apply.py:35`), едет `total_return`, бумага уезжает не в тот квартиль.

Дополнительно (`src/ingest/splits.py:134`): ключ дедупа включает коэффициент
`(date, before, after)`. Если ISS исправит `before/after` на ту же дату, старая
запись останется, новая добавится, и `cascade_for_dates` (`apply.py:44`) перемножит
**оба** коэффициента. Для сплита 1:10, исправленного на 1:100, это ошибка в 1000×.

## Что сделать

1. Добавить `force` в `_read_iss_payload` и `--force-refresh` в CLI — по образцу
   `ingest dividends`. Временная мера; постоянная — единый клиент из `task 040`.
2. **Разово прогнать с очищенным кэшем** и разобрать, что прилетит за апрель–сентябрь.
   Пока не прогнали, мы не знаем, есть ли ущерб в данных.
3. Ключ дедупа сменить на `(date, source)`; при расхождении `before/after` на ту же
   дату — падать с указанием тикера и даты, а не тихо добавлять вторую запись.
4. Тест `tests/test_splits.py:327` сейчас фиксирует дефект (`assert len(calls) == 1`).
   Переписать на «без флага кэш переиспользуется, с флагом перезапрашивается».

## Результат прогона (2026-09-05)

Ущерба нет. Разведка read-only: свежий payload против кэша от 10 мая —

```
строк в кэше от 10 мая: 55
строк сейчас:           56
новых:      ('2026-07-02', 'CRWD-RM', 1, 4)
исчезнувших: нет
```

Единственная новая строка за четыре месяца — `CRWD-RM`, иностранная расписка. Суффикс
`-RM` отсекается `_is_equity_secid` (`splits.py:57`), то есть в `data/splits/` она не
попала бы и при работающем кэше.

Сквозная проверка: `momentum ingest splits --force-refresh` сходил в сеть,
`git status --porcelain data/` пуст. Ни одной пропущенной записи по девяти
ISS-тикерам.

Вывод: дефект был реальный и мог стоить дорого, но выстрелить ему было нечем —
на бирже за эти четыре месяца не произошло ни одного сплита среди отслеживаемых бумаг.

## Сделано

- `force` в `_read_iss_payload` + `--force-refresh` в CLI.
- Ключ дедупа `(date, before, after)` → `date`. Сплит дважды в один день невозможен,
  так что это настоящий инвариант. Проверено перед сменой: во всех 11 файлах ровно по
  одной записи, дубликатов дат нет.
- Изменённый ISS коэффициент на ту же дату теперь падает с указанием тикера, даты и
  обоих отношений вместо тихого добавления второй записи (которую
  `apply.cascade_for_dates` перемножил бы с первой).
- Ручная запись выигрывает у ISS на ту же дату при любом отношении, с WARN при расхождении.
- `tests/test_splits.py:327` фиксировал дефект (`assert len(calls) == 1`) — теперь
  проверяет обе стороны. Плюс два теста: на падение при смене коэффициента и на
  приоритет ручной записи.
- README: флаг в §Monthly update и в таблице CLI.
- Runbook скилла (`references/ingest_prices.md`): флаг + пояснение, почему он обязателен.

## Осталось

Постоянное решение — единый ISS-клиент из `task 040`, который раздаст `force` всем
четырём модулям ingest. До него эта заплатка держит.
